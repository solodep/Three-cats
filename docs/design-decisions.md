# Проектные решения безопасности

Черновик для EK1. Все D ниже относятся к планируемому ядру [Three-cats Events](../PROJECT.md). В текущем сервере есть только `/health`: вход, БД, права и регистрации ещё не реализованы. Проверки ниже являются планами, а не выполненными тестами.

## D-01

### Личность, права на объект и состав ответа проверяет сервер

**Контекст:** вход в систему и роль организатора не дают права распоряжаться чужими объектами. Даже правильная проверка приватного маршрута не защищает от случайного раскрытия регистраций в публичном ответе.

**Решение:**

- использовать стандартную аутентификацию ASP.NET Core Identity с bearer-токенами; локальные учебные аккаунты и роли подготавливает сервер;
- брать пользователя только из проверенного контекста, владельца и роль — из серверных сведений;
- для чтения/отмены регистрации проверять `Registration.UserId == currentUser.Id`;
- для создания события требовать роль организатора; для черновика, публикации, закрытия и списка участников — дополнительно `Event.OrganizerId == currentUser.Id`;
- на всех защищённых маршрутах отказывать без установленного разрешения; проверка находится до чтения приватного ответа и изменения состояния;
- определять отдельные DTO для публичных событий, собственных регистраций и списка участников. Не сериализовать сущности БД вместе с навигационными свойствами;
- не принимать владельца и роль из предметного JSON; лишние поля отклоняются по D-03.

**Обоснование:** контроль относится к конкретному действию и объекту. Прямой запрос действует по тем же правилам, что и любой интерфейс. Ограниченный DTO защищает публичный путь, на котором аутентификация не нужна.

**Связанные угрозы:** [T-01](threat-model.md#t-01), [T-02](threat-model.md#t-02), [T-03](threat-model.md#t-03), [T-08](threat-model.md#t-08).

**Связанные требования:** [SR-01](security-requirements.md#sr-01), [SR-02](security-requirements.md#sr-02), [SR-03](security-requirements.md#sr-03), [SR-04](security-requirements.md#sr-04).

**Альтернатива:** фильтровать недоступные операции в клиентском интерфейсе. Она полезна для удобства, но не обеспечивает SR при прямом запросе, поэтому серверная проверка сохраняется независимо от клиента.

**Допущения и ограничения:** корректно настроены проверка токенов и серверное хранение ролей; секреты и ключи токенов не публикуются. Кража действительного токена на устройстве пользователя этим решением не предотвращается. При размещении вне localhost понадобятся HTTPS и пересмотр среды. Пароли хеширует стандартный механизм Identity; собственной криптографии нет. Механизм хранения ключей уточняется при реализации входа.

**Будущие проверки:**

1. Подготовить A и B как участников, O1 и O2 как организаторов; дать O1 собственное событие, B — регистрацию. Прямые запросы A на чтение/отмену записи B и O2 на черновик/закрытие/список события O1 должны получить отказ без изменения состояния и без приватных полей. Допустимые запросы владельцев выполняются согласно SR-02–SR-04.
2. Без токена и с изменённым токеном выполнить защищённое действие: отказ, записей нет. Затем передать `UserId`, `OrganizerId` или `Role` обычным предметным полем: отказ по D-03. Допустимый запрос создаёт объект от имени установленного пользователя.
3. Прочитать публичный каталог и карточку без входа. Проверить весь JSON, включая вложенные объекты: только публичные поля, без регистраций, аккаунтов, хешей и токенов. Добавление навигационного свойства в модель БД не должно менять публичный DTO.

## D-02

### Регистрации и состояние события изменяются атомарно

**Контекст:** отдельная проверка свободного места и последующая запись позволяют двум запросам занять последнее место. Повтор отмены опасен, если сервер каждый раз увеличивает отдельный счётчик свободных мест.

**Решение:** в SQLite все операции записи, влияющие на событие и регистрации, проходят транзакцию с ранним получением блокировки записи (`BEGIN IMMEDIATE` либо эквивалентный режим провайдера). Внутри неё сервер заново читает событие, проверяет состояние и время, находит собственную регистрацию, считает активные записи и только затем создаёт/активирует запись. Проверка и изменение завершаются одним commit; сбой приводит к rollback.

Для пары `(EventId, UserId)` задаётся уникальное ограничение в БД. Отмена меняет только `active → cancelled`; уже отменённая запись остаётся без изменения. Число занятых мест вычисляется по активным регистрациям, отдельного изменяемого счётчика нет. Публикация и закрытие используют тот же порядок блокировки. При занятой БД допускается ограниченное ожидание, затем отказ без частичного изменения; это не считается успешной регистрацией.

**Обоснование:** два записывающих запроса не принимают решение на одном устаревшем состоянии. Блокировка действует на уровне БД, поэтому защищает и при двух процессах, обращающихся к одному файлу. Уникальное ограничение и переход состояния защищают от повторов. Последовательность «проверка → вставка» без указанной гарантии недостаточна.

**Связанные угрозы:** [T-04](threat-model.md#t-04), [T-05](threat-model.md#t-05), [T-06](threat-model.md#t-06).

**Связанные требования:** [SR-05](security-requirements.md#sr-05), [SR-06](security-requirements.md#sr-06), [SR-07](security-requirements.md#sr-07).

### Сравнение двух применимых способов учёта мест

| Способ | Гарантия при корректной реализации | Цена и ограничение |
| --- | --- | --- |
| A: считать активные регистрации внутри транзакции с блокировкой записи | Проверка и запись используют одно согласованное состояние; отдельного счётчика нет | Подсчёт зависит от числа записей; SQLite сериализует записи даже для разных событий |
| B: хранить число занятых мест и атомарно менять его вместе с регистрацией | Условное увеличение допускается только ниже вместимости; уменьшение — только при действительном переходе `active → cancelled` | Быстрый доступ к числу, но все пути обязаны согласованно менять два объекта; повтор или частичный сбой без транзакции создаёт расхождение |

Оба способа применимы при транзакции, уникальной паре и корректном переходе состояний. Выбран A: при учебной вместимости до 1000 проще проверять инвариант по фактическим записям. Выбор пересматривается, если замеры покажут неприемлемую стоимость подсчёта или конкуренцию записей разных событий; тогда нужны повторное сравнение хранения и нагрузочная проверка, а не автоматическое добавление счётчика.

### Контрпример, уточнивший первоначальную идею

**Исходное предположение:** после успешной отмены клиент не отправит тот же запрос ещё раз; можно просто уменьшать счётчик занятых мест.

**Контрпример:** вместимость 1. A зарегистрирован, отменяет запись, но ответ теряется. Клиент повторяет отмену. Если каждый запрос уменьшает счётчик, после повторной отмены возникает возможность успешно зарегистрировать и B, и C при одном месте.

**Уточнение цепочки:** угроза T-05 учитывает не только повтор регистрации, но и повтор отмены. SR-05 и SR-06 требуют сохранения инварианта и идемпотентной отмены. D-02 считает активные записи и допускает только настоящий переход состояния; план проверки включает потерю ответа и повтор. Это разбор проектной идеи; искусственная уязвимость в код не добавлялась.

**Допущения и ограничения:** все обработчики записи используют один режим транзакций, уникальное ограничение реально создано в БД, никто из клиентов не изменяет файл напрямую. Время берётся с сервера при проверке внутри транзакции; гарантия относится к этому моменту, а не к мгновению доставки ответа. SQLite и один файл пригодны для небольшой локальной нагрузки, а не для неограниченного числа параллельных событий.

**Будущие проверки:**

1. На событии с одним оставшимся местом одновременно отправить запросы разных пользователей. Ожидать одну успешную новую регистрацию и неизменный инвариант SR-05. Повторить с двумя процессами сервера и одним файлом БД: запрет лишней записи должен сохраняться.
2. Повторить регистрацию одного пользователя последовательно и одновременно: в БД одна пара и одно занятое место. Отменить её дважды; затем отправить регистрации B и C на событие вместимостью 1. Успешна только одна запись; отменённая запись A не занимает место.
3. Остановить регистрацию после чтения состояния внутри транзакции, параллельно начать закрытие. Выпустить блокировку: результат соответствует порядку commit. После зафиксированного закрытия новая регистрация всегда отклоняется. При достижении времени начала до проверки операция также отклоняется.
4. Прервать выполнение перед commit и открыть БД заново. Ни регистрация, ни изменение состояния не остаются частично применёнными. Законная отмена до начала остаётся доступной после закрытия новой записи.

## D-03

### Ввод ограничивается, строки передаются как данные

**Контекст:** внешнее тело запроса может быть большим, содержать лишние поля, некорректный JSON или SQL-подобные строки. Права пользователя не делают эти данные доверенными.

**Решение:**

- задать предел тела предметного запроса 32 KiB до десериализации;
- использовать отдельные DTO с разрешёнными полями; неизвестные поля JSON отклонять, не привязывать вход напрямую к сущности БД;
- перед записью проверять типы и предметные пределы паспорта: название 1–120 символов после trim, описание до 2000, вместимость 1–1000, время UTC в будущем;
- выполнять запросы через параметризованные операции EF Core; не собирать SQL конкатенацией строк;
- возвращать стабильную ошибку без внутренних деталей; неожиданные исключения не превращать в успешное изменение состояния. Секреты и токены не включать в ответ и прикладное журналирование.

**Обоснование:** допустимая структура ограничивает массовое присваивание полей, предел тела ограничивает обработку одного запроса, параметризация сохраняет различие данных и команды. Экранирование кавычек вручную или «очистка опасных слов» не заменяют параметризацию.

**Связанные угрозы:** [T-01](threat-model.md#t-01), [T-07](threat-model.md#t-07), [T-09](threat-model.md#t-09).

**Связанные требования:** [SR-01](security-requirements.md#sr-01), [SR-08](security-requirements.md#sr-08), [SR-09](security-requirements.md#sr-09).

**Допущения и ограничения:** все предметные маршруты используют эти правила; ограничения проверяются на сервере. Размер одного тела не ограничивает число запросов и не обеспечивает устойчивость к распределённой нагрузке. Публичное размещение потребует отдельного решения по частоте, окружению и доступности.

**Будущие проверки:**

1. С действительным пользователем отправить тело 32 KiB + 1 байт и синтаксически неверный JSON: отказ, состояние БД прежнее, внутренних подробностей нет.
2. Проверить пустое название, 121 символ, описание 2001 символ, вместимость 0 и 1001, прошедшее начало и лишний `Role`: отказ без записи. Проверить допустимые граничные значения с будущим временем и требуемыми правами: создание выполняется.
3. Создать собственный черновик с SQL-подобным названием допустимой длины. Прочитать его через разрешённый маршрут: текст сохранён буквально, чужие события и регистрации не менялись. Просмотреть запросы реализации: нет конкатенации входа с SQL.
4. Вызвать отказ хранилища на тестовом стенде: ответ не содержит строку подключения, stack trace или данные входа, успешная запись не заявляется.

## Что подтверждено сейчас

Сборка и HTTP-проверка `/health` могут подтвердить только наличие технической основы. Все проверки D-01–D-03 выполняются после реализации соответствующих механизмов. Человеческая проверка содержания и индивидуального вклада ещё предстоит; документы сами по себе не подтверждают работу защиты и не гарантируют оценку.
